已确认的核心能力包括：

- 单笔 10 mojo funding coin 可按 Claim 分支结算为 Merchant 1 mojo、User 9 mojos。
- 无 Voucher 时，Refund 分支可将完整 10 mojo 返回 User。
- User 与 Hub 离线后，Merchant 可仅凭持久化 Voucher 独立构造 Claim。
- Claim 与 Refund 高度互斥，重复花费、跨网络、跨通道和篡改输入均被拒绝。
- SQLite 状态机支持去重、原子迁移、广播中间态和重启恢复。
- 模拟器全量验收通过；真实主网已完成各 1 次 Claim 和 Refund，但尚未完成 Stage A 要求的连续性和重组演练。

- 主网本地 full node mTLS 连接；仓库仍保留 testnet11 公共 Coinset 探针用于开发调试。
- 网络、Genesis Challenge、同步状态和 peak 校验。
- coin record、funding coin children、广播和 mempool 查询。
- 带传输重试的确认深度轮询。
- 基于 mempool floor 的费用估算和独立 fee coin 选择。
- fee coin 找零。
- SQLite 链上观察记录、最终 children 和重组回滚证据。

2026-08-03 已完成两次 Chia 主网 10 mojo 实测：

| 场景 | 结果 | 关键证据 |
|---|---|---|
| Claim | **PASS** | 10 mojo -> Merchant 1 mojo + User 9 mojos；确认高度 9097428 |

该实测证明了真实主网签名验证、金额守恒、Claim/Refund 输出结构和链上确认路径可以工作。

## 三、阶段 B：服务化、watcher 与运营能力

### 3.1 已完成内容

当前已具备三个独立角色的 CLI：

- `user`
- `hub`
- `merchant`

角色之间通过版本化 JSON envelope 交换消息，核心 payload 仍使用固定的 Invoice、Intent、Voucher 二进制编码。已实现的运营能力包括：

- Merchant 和 User 持久化 watcher，可从 SQLite 恢复广播任务。
- Merchant 使用持久化 Voucher 构造 Claim，不需要 User 或 Hub 私钥。
- User 支持退款 watcher。
- 广播准备、SpendBundle、transaction id、尝试次数、mempool、确认和审计事件落库。
- 幂等 key 绑定 channel、操作类型和 funding coin，重复请求复用同一 SpendBundle。
- `metrics` 查询 channel、广播任务、可恢复任务、尝试、确认和重组观察数量。
- 失败注入模式 `--once`，用于 watcher 恢复和边界测试。

### 3.2 已有验证

- 进程重启后可恢复 `PREPARED`、`PENDING`、`SUBMITTED` 等广播状态。
- 数据库只在链上 children 与预期 parent、puzzle hash、金额和输出数量完全一致后进入 `SETTLED` 或 `REFUNDED`。
- Claim/Refund 竞争、重复广播和确认不匹配均有确定错误状态。

### 3.3 当前不足与阶段判断

Stage B 仍缺少生产级集成证据：

- 尚未完成断 RPC、进程崩溃、数据库损坏、磁盘写失败和乱序事件的完整实网演练。
- Merchant watcher 的费用 bump、截止高度安全余量和最终重试策略仍需在主网验证。
- Hub 的签名能力虽已类型化，但尚未形成独立签名进程或独立主机的部署闭环。
- 对外 API 的认证、限流、权限模型、告警和运营手册仍需补齐。

**阶段 B 判断：基本实现完成，待集成验收。** 当前可以作为工程化原型运行，尚不足以作为无人值守生产服务发布。

## 四、阶段 C：安全加固与发布门禁

### 4.1 已完成内容

Stage C 已建立以下安全和工程控制：

- 协议字节、规范 round-trip、畸形 artifact、金额/高度边界和随机状态迁移测试。
- CLVM tree 和 solution 解析的 panic-catching 测试。
- 两个 libFuzzer target，覆盖 protocol bytes 和 CLVM solution encoding。
- `PREPARED`、`PENDING`、`SUBMITTED` 广播状态的重启恢复和故障一致性测试。
- 幂等 key、尝试次数溢出、SQLite `i64::MAX` 边界和协议高度约束。
- `HubSigner` 类型化边界，数据库层不再直接要求 raw `SecretKey`。
- `Cargo.lock`、`deny.toml`、确定性 SBOM、security-check 脚本和 CI workflow。
- Stage C 审查发现的 refund height 截断问题已关闭，回归测试覆盖 `u64::MAX` 场景。

### 4.2 当前证据

- `cargo test --locked --all-targets`：49 passed。
- `cargo clippy --locked --all-targets -- -D warnings`：通过。
- 金额/高度溢出、签名域、CLVM 分支、coin lineage、状态迁移、崩溃恢复和模型重组测试：通过。
- Stage C 内部审查结论：当前审查范围内无未解决 P0/P1 funding-safety 问题。

### 4.3 发布门禁尚未关闭的原因

以下事项仍是正式发布阻塞项：

1. `cargo-fuzz` 尚未完成固定时长运行，缺少保留 corpus 和 crash disposition 证据。
2. `cargo-audit`、`cargo-deny` 尚未在当前环境成功执行。
3. 当前工作区尚无 Git commit/tag，缺少不可变审计版本。
4. 尚未完成独立第三方安全审计。
5. `HubSigner` 只是应用层接口，不等于进程或主机隔离；生产仍需独立 signer trust domain、认证 IPC、allowlist、限流、审计日志和密钥生命周期控制。

**阶段 C 判断：代码加固完成，正式发布门禁未通过。**

## 六、风险分级

### 高优先级

- 真实网络可靠性证据不足：尚未证明连续运行、重组回滚、RPC 故障和费用不足场景。
- 生产密钥隔离未闭环：Hub 签名进程、IPC 认证和密钥生命周期控制仍需设计和落地。
- 安全发布证据不完整：fuzz、依赖扫描、不可变 revision 和独立审计均未完成。

### 中优先级

- Chia 2.7.3 RPC 返回字段与固定 SDK 类型存在兼容性风险。
- watcher 的截止高度余量、fee bump 和告警策略尚未经过实网长时间运行。
- 当前协议仍是一次性、单商户、单笔模型，不是通用多状态支付通道。
